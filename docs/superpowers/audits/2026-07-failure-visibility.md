## (a) Bridge stops delivering punches

### Trace

**What writes Device Sync Status:**
`notify_device_sync_status` (device_sync.py:153–208) — a Bridge webhook that upserts a
`Device Sync Status` row via `upsert_device_sync_status` (device_sync.py:112–150). Fields:
`device_sn`, `local_date`, `last_device_log_at`, `last_delivered_at`, `pending_count`,
`last_error`, `bridge_env`. This is the only write path (no scheduler writes this).

**What reads Device Sync Status:**
1. `hr_calendar.py:478–509` — reads all DSS rows for the employee's branch and the
   requested week, returns them as `device_sync` in the calendar API payload.
2. Frontend `attendancePunches.ts:211–248` — `syncHorizonForTimeline()` computes:
   - `isLagging = true` if any row has `pending_count > 0`, OR
     if `last_device_log_at > last_delivered_at` for any row.
   - `horizonMin` = the earliest `last_delivered_at` across matching rows.
3. `DayTimeline.tsx:327` — `openSessionLabel()` appends `"sync pending"` to the tooltip
   text of an **open session** punch bar if `row.syncLagging` is true. No banner,
   no persistent indicator.

**What does NOT read Device Sync Status:**
- No scheduled job audits freshness ("if DSS row hasn't been updated in N hours, alert").
- No `frappe.sendmail`, `send_web_push`, or Frappe Notification is wired to DSS.
- The DocType JSON (`device_sync_status.json`) has no `actions`, no notification config,
  no assignment rules.

**The gap:**
If Bridge goes silent it stops calling `notify_device_sync_status`. The DSS row freezes
at the last-known-good value. The frontend's `syncHorizonForTimeline` compares
`last_device_log_at` vs `last_delivered_at` within the frozen row — both fields are from
the last successful update, so neither condition triggers and `isLagging` stays `false`.
There is no check like "the DSS row's `modified` is N hours old" relative to wall clock.
The "sync pending" tooltip never appears.

The only downstream signal is UNNOTIFIED_ABSENCE flags (from the 03:00 fallback
`run_company_fallback_closeout`, closeout.py:82) generated the following morning for
employees who were on shift with zero delivered checkins. That flag is per-employee, not
a "Bridge is down" signal, and appears ~18 hours after a 09:00 outage start.

**HUMAN FINDS OUT: no — no consumer of Device Sync Status checks wall-clock freshness.
The frozen watermark is invisible to the SPA. The only indirect signal is
UNNOTIFIED_ABSENCE flags the following morning (~18 h after outage start). No push, email,
or desk notification fires from within the app.**

## (b) Closeout webhook never arrives

### Trace

**Normal path:**
`notify_device_closeout_status` (closeout.py:121–171) — Bridge posts `status=closed`.
This calls `upsert_device_closeout_alert` (closeout.py:174–201) — creates/updates a
`Device Closeout Alert` row with `resolved_at=now()`. Then enqueues
`generate_auto_flags_for_device_date` (closeout.py:204–228) which writes all final flags
(`LATE_START`, `LEFT_EARLY`, `MISSING_TIME`, `ATTENDANCE_ISSUE`, etc., day_closed=1).

**When the webhook never arrives:**
No DCA row is created. `has_open_device_closeout_alert` (closeout.py:287–301) therefore
returns `False` for all employees at the branch.

`run_company_fallback_closeout` (closeout.py:82, scheduled `daily` at 03:00) runs and
calls `_generate_company_fallback_for_date` (closeout.py:246–284). For each active
employee:
- If the employee has an open DCA at their branch → **skip** (closeout.py:253). With no
  DCA row at all this guard never trips — the fallback proceeds.
- If no shift assignment → skip.
- **If checkins present → skip** (closeout.py:261). These employees get **nothing** —
  LATE_START, LEFT_EARLY, and MISSING_TIME are only generated by the device closeout path.
- If no checkins → creates one `UNNOTIFIED_ABSENCE` flag (`day_closed=1`).

**Notification chain for the fallback:**
`_insert_flag` (closeout.py:615–631) inserts an Attendance Flag row. No email, push, or
desk notification follows. The Device Closeout Alert DocType JSON has no `notify_by_email`,
no assignment rules, and no doc events in hooks.py. `send_web_push` (webpush.py:93) is
not called from any closeout or fallback path — the only caller beyond the test endpoint
is `send_test_push` (webpush.py:63).

**Frontend visibility:**
WeekView.tsx:210–216 shows a `"!"` badge for days that have unresolved Device Closeout
Alerts. Since no DCA row was created (webhook never arrived), no `"!"` badge appears.
HR sees a clean calendar with no indicator that the device day was never properly closed.

**HUMAN FINDS OUT: partially — The 03:00 fallback fires and writes UNNOTIFIED_ABSENCE
for zero-checkin employees. Employees with any checkins (even partial) silently miss
LATE_START, LEFT_EARLY, and MISSING_TIME flags — those are only produced via the device
closeout path. No Device Closeout Alert row is created, so no "!" badge appears in the
SPA. No email, push, or desk notification fires for the missed closeout. Detection depends
on an HR reviewer actively noticing missing final flags; no proactive alert fires.**

## (c) Scheduler itself stops (worker down / site paused)

### Trace

**Registered scheduler jobs** (hooks.py:106–115):
- `*/30 * * * *` → `dewey_time.attendance_engine.intraday.run_intraday_scheduler`
- `daily` → `dewey_time.attendance_engine.closeout.run_company_fallback_closeout`

**Doc events still fire regardless** (hooks.py:117–121):
`Employee Checkin.after_insert` and `.on_update` → `intraday.on_employee_checkin_after_insert`
/ `on_employee_checkin_on_update`. These are doc events, not scheduler-driven. Individual
checkin-triggered intraday runs continue even if the scheduler is dead.

**What breaks if the scheduler stops:**
- No 30-min batch intraday runs. Provisional flags go stale; only per-checkin doc-event
  runs fire (covering the inserting employee only, not the full company sweep).
- The 03:00 `run_company_fallback_closeout` never runs → no UNNOTIFIED_ABSENCE flags
  generated for any employee the next morning.

**Dead-man's switch / heartbeat:**
There is none in the app code. No scheduled job writes a "last_ran_at" heartbeat. No
job checks "has intraday fired in the last 60 minutes?" No frappe.sendmail,
`send_web_push`, or Notification Log entry is created on scheduler skip or delay. The
Device Sync Status and Device Closeout Alert doctypes have no scheduler-health fields.

**Frappe Cloud / infra coverage:**
Frappe Cloud monitors worker processes and may send emails on worker death at the infra
level. **This cannot be determined from app code** — verify with Frappe Cloud docs /
user. From the app's own code there is zero visibility.

**HUMAN FINDS OUT: no — from app code there is no dead-man's switch. Scheduler stopping
causes stale intraday flags (batch runs stop) and no nightly closeout (UNNOTIFIED_ABSENCE
never generated), all silently. The SPA will show unchanged provisional flags but gives
no "scheduler down" indicator. Frappe Cloud infra may alert on worker death, but this is
outside app code — cannot determine from code alone; verify with infra.**
